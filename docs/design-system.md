# 视觉规范 v4（Design System）

> **唯一视觉事实来源。** 任何界面改动先读本文；`npm run design:check` 静态门禁逐条对应 §5。历史审计与实施记录见 [design-audit-v4.md](archive/design-audit-v4.md)。

## 5. 设计规范 v4

### 5.1 字阶：5 档，全部使用 Tailwind 原生类

| 角色 | 类名 | 尺寸 | 用途 |
|---|---|---|---|
| `display` | `text-3xl` | 30px | 欢迎页主标语（全应用唯一一处） |
| `title` | `text-xl` | 20px | 功能页标题（**必带 icon**）、设置中心页标题 |
| `heading` | `text-base` | 16px | 段落标题、卡片标题、教程 step 标题 |
| `nav` | `text-base` | 16px | 侧栏导航项、页签项、欢迎页卡片标题 |
| `body` | `text-sm` | 14px | 正文、输入框、按钮、表单标签、列表项 |
| `caption` | `text-xs` | 12px | 元信息：计数、路径、单位、状态徽标、快捷键 |

**6 个角色，5 个尺寸**（`heading` 与 `nav` 同尺寸、靠字重区分）。

尺寸阶梯：`12 → 14 → 16 → 20 → 30`
比值：`1.17 / 1.14 / 1.25 / 1.50`

**像素映射已核验**（`tailwind.config.js` **未覆盖** `fontSize`，故按 Tailwind 默认解析）：

| 类名 | 解析值 | px |
|---|---|---|
| `text-xs` | `0.75rem` | **12px** ✅ |
| `text-sm` | `0.875rem` | **14px** ✅ |
| `text-base` | `1rem` | **16px** ✅ |
| `text-xl` | `1.25rem` | **20px** ✅ |
| `text-3xl` | `1.875rem` | **30px** ✅ |

**为什么是这 5 档**：它们是 Tailwind 的默认档位，本就可直接使用。用原生类的意义不只是省事——
**它让"随手写个 `text-[13px]`"变成一件需要刻意为之的事**，从机制上堵住漂移。

**明令禁止**：`text-[Npx]` 任意值。若某处确实需要第 6 个尺寸，
必须先改本文件、评估全应用影响，再落地——不允许局部先斩后奏。

### 5.2 字重：3 档

| 字重 | 类名 | 用途 |
|---|---|---|
| 400 | `font-normal` | 正文、说明、列表 |
| 500 | `font-medium` | 导航项、按钮、表单标签、强调 |
| 600 | `font-semibold` | 全部标题（display / title / heading） |

**废弃 700（`font-bold`）。** 现状 700 只用在两处：欢迎页主标语、教程数字徽标。
二者用 600 已足够，而 4 档字重叠在 5 档字阶上只会制造噪声。

### 5.3 文字色：规范改为规定「目标对比度」，不再规定透明度

这是 v4 对旧规范最重要的方法修正。旧规范写「次 62% / 弱 38%」——
数字既与代码不符，`38%` 算下来只有约 2.3:1，**规范本身在教人违反无障碍标准**。

v4 规定目标，token 值只负责实现：

| 语义 | 目标对比度 | 浅色实现 | 实测 | 暗色实现 | 实测 |
|---|---|---|---|---|---|
| `text-1` 标题级 | ≥ 12:1 | `#0F1B33` | **17.14:1** ✅ | `#E8EEF9` | **15.84:1** ✅ |
| `text-2` 正文级次要 | ≥ 7:1 | `rgba(15,27,51,.78)` | **8.47:1** ✅ | `rgba(232,238,249,.72)` | **8.56:1** ✅ |
| `text-3` 辅助级 | ≥ 4.5:1 | `rgba(15,27,51,.64)` | **4.84:1** ✅ | `rgba(232,238,249,.58)` | **4.95:1** ✅ |

**改动的部分加粗**：`text-3` 由 `52% → 64%`（浅色）、`36% → 58%`（暗色）。

> **⚠️ 目标对比度必须在「它可能落到的最差的底」上核算，不是常态那个底。**
> v4 把 `text-3` 浅色定在 60%，在静止的画布底上量到 4.55:1 就收工了。但列表行在
> hover 时会换成 `--surface-hover`、按下时换成 `--surface-active`——同一个 60% 在那两个
> 底上只有 **4.37:1 / 4.28:1，低于 AA**（暗色 52% 在 hover 底上是 4.47:1，同样不达标）。
> 也就是说 `text-ink-3` 用在**任何可 hover 的行里**都曾经是违规的，而 v4 的对比度脚本
> 只测了静止态——「241 个节点 0 失败」是**假阴性**。
> v4.1 改为 `64% / 58%`，最差底 4.84:1 / 4.95:1，并由 `npm run design:check` 静态守住
> （它会把 `--text-N` 对 `--surface-1 / -hover / -active` 逐个核算，取最差值判定）。

明暗主题仍可用不同透明度（明暗感知本就不同），但**必须各自达标**，
且差异需有据（不再出现"浅色 78% / 暗色 60%"这种无记录的偏差）。

### 5.4 语义色：填充色与文字色分离

现状把语义色直接当文字色用，导致 4 个语义色全部不达标。
v4 拆成两套：

| 语义 | 填充/图标（原色） | 文字版·浅色底 | 实测 | 文字版·暗色底 | 实测 |
|---|---|---|---|---|---|
| success | `#2FA35C`（**填充已无使用点**，见下） | `#187A42` | **5.38:1** ✅ | `#46B97C` | **7.46:1** ✅ |
| danger | `#DA3733` | `#B3261E` | **5.59:1** ✅ | `#FA6B6B` | **5.31:1** ✅ |
| warning | `#E6A23C` | `#8F5F00` | **5.05:1** ✅ | `#EDB05E` | **9.64:1** ✅ |
| accent-2 | `#F37021` | `#C2410C` | **5.18:1** ✅ | `#8AA2FF` | **7.00:1** ✅ |

**规则：语义色用于文字时一律用 `-text` 变体；用于图标、填充、底色、进度条时用原色。**
暗色主题下原色本身已达标，故两套合并（`-text` 变体仅浅色主题需要）。
（v4.2 例外：`--danger-text` 暗色不再合并，见下。）

> **v4.2：danger 两主题统一成一个红 `#DA3733`，而且这次不是审美口味**
>
> v4.1 是浅 `#E5484D` / 暗 `#F2666B`。两个都有同一个毛病：**蓝通道比绿通道高 5**
> （72/77 与 102/107），在深色画布上读起来就是「玫红」而不是「红」——这是用户的原话。
> 而且两个都撑不住白字（**3.91:1 / 3.05:1**，都低于 AA）。
>
> 统一后的 `#DA3733` 满足两件事：`G(55) > B(51)` 是正红，白字 **4.59:1** 达标。
> 于是 `Button` 的 danger 变体（「确认删除」「确认清理」，4 处）**在明暗两主题都合法**，
> 不需要 `--on-danger` 这类新 token。（这次是把它压深到达标，而不是把字改深色——
> 亮红填充 + 深色字会改变浅色主题的观感，用户明确说浅色那个红按钮没问题。）
>
> 暗色 `--danger-text` 仍要单独取 `#FA6B6B`：`hover:text-danger-text hover:bg-danger-soft`
> 有 5 处调用（`LeftPane` / `VoiceClone` ×2 / `TextToSpeech` / `DropdownMenu`），
> 红字压在红 tint 上、且 tint 叠在卡片上，填充红只有 4.06:1。`#FA6B6B` 取 `G = B`，
> 是浅红而不是玫红。

> **v4.2：`--success` 从此只当文字色，不再当填充色**
>
> 上表里 success 的「填充/图标」列现在**没有任何使用点**。原先有三处把它当填充用——
> 都是同一个组件：输入框旁边那颗 24px 绿色圆钮，里面一颗 `<Check size={12} strokeWidth={3}/>`：
>
> | 位置 | 用途 |
> |---|---|
> | `VoiceClone.tsx:658` | 确认重命名分类 |
> | `VoiceClone.tsx:762` | 保存音色角色弹窗内确认新建分类 |
> | `AudioTagMenu.tsx:105` | 确认添加自定义标签 |
>
> 问题出在暗色：`--success` 为了能在暗色画布上当文字被调亮到 `#46B97C`，
> 而白勾压在它上面只有 **2.47:1**，低于图形对比的 3:1（浅色 `#2FA35C` 是 3.22:1，合法）。
> 一棵绿同时被要求「当浅底上的文字」和「当白勾的填充」，暗色下必然牺牲一头——
> 与 §5.4 里 accent 曾经的问题同源。
>
> **决定：这三处不该有绿色。** 它们是「确认」动作，不是「成功」状态——绿色在这里
> 只是一句「这个能点」，而确认动作在本设计系统里已经有一个唯一写法。改为
> `bg-accent-strong text-accent-on hover:bg-accent-hover`（浅色克莱因蓝 + 白勾 10.69:1，
> 暗色爱马仕橙 + 深勾 6.61:1），并与同排的「取消」(`text-ink-3 hover:text-danger-text`) 成对。
> 尺寸统一 **24px**（`AudioTagMenu` 那处原本是 20px，不在图标按钮档位表里）。
>
> 判据（`AGENTS.md` 的「装饰性标识不许借语义调色板」）：**语义色的前提是有真实状态。**
> 这三颗钮不表达成功，绿就是装饰性借用。`--success-soft` 更是从未被任何组件使用过。
> `--success-text` 仍有三处真实用途（Toast 成功提示、历史记录「音转文」徽标、
> 设置中心「已配置」），所以绿色作为**文字色**保留。

> **实施期发现的关键不变式（本文件最初漏掉，实测补上）**
>
> **每个 `-text` 变体必须在其配套的 `-soft` 底上达到 4.5:1，只在白底达标是不够的。**
>
> 原因是设计系统**按构造把两者配成对**：`bg-success-soft text-success-text` 就是徽标/头像的标准写法。
> 最初按「白底达标」选的 `#1A7F45`(5.04:1)、`#9A6700`(4.87:1) 白底都过，
> 但叠到自己的 soft 底上（`rgba(47,163,92,0.11)` / `rgba(230,162,60,0.12)`）后
> 实测掉到 **4.37:1 / 4.46:1，双双不达标**——是音色头像首字暴露出来的。
>
> 修正后：`--success-text: #187A42`、`--warning-text: #8F5F00`，两者在自己的 soft 底上分别为
> 5.38:1 / 5.05:1，白底仍更高。`danger-text`(5.65:1) 与 `accent-2-text`(4.67:1) 本来就过，未动。
>
> 教训：**token 的验收场景要按它实际的配对用法来测，不能只在白底上测。**

新增 token：

```css
/* src/index.css */
:root {
  --success-text: #187A42;
  --danger-text:  #B3261E;
  --warning-text: #8F5F00;
  --accent-2-text:#C2410C;
}
[data-theme="dark"] {
  --success-text: var(--success);
  --danger-text:  var(--danger);
  --warning-text: var(--warning);
  --accent-2-text:var(--accent-2);
}
```

并需在 `tailwind.config.js` 的 `colors` 里补出对应类名
（**当前未配置，不补则 `text-success-text` 这类类名不存在**）：

```js
// tailwind.config.js -> theme.extend.colors
success: { DEFAULT: 'var(--success)', soft: 'var(--success-soft)', text: 'var(--success-text)' },
danger:  { DEFAULT: 'var(--danger)',  soft: 'var(--danger-soft)',  text: 'var(--danger-text)'  },
warning: { DEFAULT: 'var(--warning)', soft: 'var(--warning-soft)', text: 'var(--warning-text)' },
'accent-2': { DEFAULT: 'var(--accent-2)', soft: 'var(--accent-2-soft)', text: 'var(--accent-2-text)' },
```

#### 主题色：明暗两个主题主次对调（v4.2 新增）

品牌是两个颜色——克莱因蓝 `#002FA7` 与爱马仕橙 `#F37021`。v4.2 起**两个主题都同时保留这两个色，
变的只是谁当主角**：

| | `--accent`（主题色：主按钮 / 激活态 / 焦点环） | `--accent-2`（次色：标签 / 装饰） | `--on-accent-strong`（实心主色上的字） |
|---|---|---|---|
| 浅色 | 克莱因蓝 `#002FA7` | 爱马仕橙 `#F37021` | `#FFFFFF`（10.69:1） |
| 暗色（v4.2） | **爱马仕橙 `#F37021`** | **克莱因蓝系 `#8AA2FF`** | **`#170A03`（6.61:1）** |

**暗色必须换字色，这是最容易漏的一处。** 白字放在 `#F37021` 上只有 **2.97:1**，
而主按钮 `Button` 的 primary 变体写法是 `bg-accent-strong text-accent-on`——
只要 `--accent-strong` 变成橙、`--on-accent-strong` 还留着继承来的 `#FFFFFF`，
全应用的主按钮会**集体低于 AA**。近黑画布上的亮橙实心 + 近黑字（6.61:1）
既合法也是更强的观感，所以暗色把它改成 `#170A03`。

**由此得出一条组件红线：实心主色上的文字一律用 `text-accent-on`，不许写 `text-white`。**
`text-accent-on` 在浅色下求值就是 `#FFFFFF`（像素级不变），在暗色下自动变近黑。
v4.2 改了 4 处（录屏按钮 ×2、`Chip` 的编辑角标、`TextToSpeech` 的试听中角标）。

暗色画布是**严格中性**的：`--bg-canvas: #0A0A0B`，实测通道差 **1/255**（R=10,G=10,B=11）。
v4.1 的 `#0D1420` 是 2.5 倍蓝的红黑比（饱和度 0.59），三层表面、辉光、`--surface-active`
与 `--accent` 全是蓝的——那其实是一套海军蓝主题。现在除主题色本身外，**表面与文字一律 R=G=B**。

### 5.5 圆角：3 档，必须用命名类

| 角色 | 类名 | 值 | 用途 |
|---|---|---|---|
| 控件 | `rounded-sm` | 8px | 按钮、输入框、下拉触发器、页签项、图标按钮、骨架块、焦点环 |
| 卡片 | `rounded-md` | 12px | 卡片、Segmented 容器、下拉面板内层 |
| 大面 | `rounded-lg` | 16px | 主面板（`.mat-panel`）、弹窗与浮层（`.mat-overlay`） |
| 胶囊 | `rounded-full` | 9999px | 徽标、Chip、头像、圆形图标按钮 |

**废弃** `6px / 9px / 10px`（现状 23 处，全部出现在 TSX 的任意值写法里）。
`rounded-xl`(20px) 当前零使用——**保留在 config，标注为预留，不得随意取用**。

> **审计修正（自查发现）**：本方案初稿曾把 16px 写成"预留、未使用"。
> 逐行核对 `index.css` 后发现 `.mat-panel`（行 163）与 `.mat-overlay`（行 181）
> **本来就在用 16px，且属于档位内**——是初稿错了，不是代码错了。
> 事实是：**`index.css` 里的圆角全部合规**（8/12/16/full），
> 偏离只发生在 TSX 手写像素值上。这正是"以事实为准、不以任何一边为准"的实例。

**明令禁止**：`rounded-[Npx]` 任意值。档位外的尺寸一律不批。

**判定规则（实施期补充）**：审计里有 13 处 `rounded-[10px]` 正好卡在 8px 与 12px 之间，
无法机械映射，故定下这条可复用的判据：

- **可点击的一律 `rounded-sm` 8px**——按钮、页签项、列表行、图标按钮、输入框、下拉项
- **只承载内容的用 `rounded-md` 12px**——卡片、拖放区、多行文本域、Segmented 容器、下拉面板
- **多行文本域（Textarea）归 12px**：它虽然可输入，但面积与卡片同级，8px 会显得局促

按此规则，13 处 10px 全部归入 8px——它们逐个核过，都是可点击控件（侧栏导航项、图标按钮、
历史条目行、音色条目行、注册链接块）。

> **⚠️ 命名陷阱（已核验）**：本项目 `borderRadius` 被**整体重映射**过，
> 与 Tailwind 默认值完全不同。按默认档位的心智模型写代码会静默出错：
>
> | 类名 | Tailwind 默认 | **本项目实际** |
> |---|---|---|
> | `rounded-sm` | 2px | **8px** |
> | `rounded-md` | 6px | **12px** |
> | `rounded-lg` | 8px | **16px** |
> | `rounded-xl` | 12px | **20px** |
>
> 写代码时**只以上表「本项目实际」列为准**。
> 顺带一提：现状里那 8 处 `rounded-[6px]`，恰好等于 Tailwind 默认的 `rounded-md`——
> 这正是命名错位最容易催生的写法。

### 5.6 间距与栅格：保持 4px 网格（现状良好，无问题）

审计未发现间距混乱。沿用现状：`gap`/`p`/`m` 只用 4 的倍数（`1/2/2.5/3/4/5/6`）。
**不新引入 8px 之外的栅格体系。**

### 5.8 图标档位（v4.1 新增）

字号与圆角有档位，**图标此前完全没有**——这正是「功能页左上角 icon 太小」的根因：
没有标尺，就只能逐个凭感觉给数。实测普查 `size={N}` 用了 **14 种尺寸**。

图标档位与**它所伴读的文字**绑定，取最近的一档：

| 档位 | 用途 | 伴读对象 |
|---|---|---|
| **12px** | meta：caption 内联图标、24px 图标按钮、chip 内部小图标 | caption(12px) |
| **14px** | control：按钮 / 下拉项 / 搜索框 / 页签 / pill / chevron / 28px 图标按钮 | body(14px) |
| **16px** | nav：侧栏导航项、标题栏窗口控制、设置中心页签、Toast、≥32px 图标按钮 | nav(16px) |
| **24px** | illustration：空态与拖放区插图 | —（无伴读文字）|
| **30px** | **功能图标**：工具的标识（欢迎页卡片与该功能页页头各一次） | 两行「标题+说明」块 |

**三条判定规则**：

1. **图标跟随它伴读的文字档位。** 12px 文字配 12px 图标，14px 文字配 14px 图标，
   16px 导航文字配 16px 图标。混用（如 14px 文字旁放 12px 图标）算漂移。
2. **伴读多行块时，按块高定尺寸，不按标题字号定。**
   功能页页头是 20px 标题 + 14px 副标题构成的 **约 50px 两行块**，
   故功能图标取 **30px**（块高的 0.6，且垂直居中）。
   若只按 20px 标题去配 20px 图标，相对整块只有 0.4，看上去就是「太小」——
   这正是本次修正的由来。**规则 2 优先于规则 1。**
3. **图标按钮（无伴读文字）按按钮边长取档**，约取其一半：
   24px(`w-6 h-6`) → **12**；28px(`w-7 h-7`) → **14**；32/36px(`w-8/w-9`) → **16**。
   规则 3 只在没有伴读文字时启用。

**实测终态**（生产构建，7 屏 × 双主题）：

| 指标 | 结果 |
|---|---|
| 渲染图标总数 | **359 个 `svg`**（数量远大于静态 `size={N}` 的 83 处——列表行会重复渲染，且部分图标经 props 传入。**须用 §7 的数据 fixture**，空列表时只有 163）|
| 在用图标尺寸 | **12 / 14 / 16 / 24 / 30 / 36**，恰好 6 档（v4.3.2 新增 36：首页三张功能卡，那是唯一一处"图标本身是主角"的位置）|
| 档位外尺寸 | **0** |
| 静态 `size={N}` 分布 | 12×26、14×33、16×16、24×5、30×3 |

> 用 DOM 量而不是只数源码，是因为**没写 `size` 的图标会静默落到 lucide 默认的 24**——
> 只做静态普查会漏掉这类，而 24 恰好在档位内，漏了也看不出来。

### 5.9 图标按钮与 hover 文案（v4.1 新增）

**① 无文字的图标按钮必须有 hover 文案。** 图标不解释自己；`aria-label` 只服务屏幕阅读器，
肉眼看不见。统一用应用内的 `Tooltip` 包一层：

```tsx
<Tooltip label="删除">
  <button aria-label="删除" …><Trash2 size={12} /></button>
</Tooltip>
```

`aria-label` 仍然要留——它是**无障碍名**，不是文案，两者并存、不互相替代。
`design:check` 会扫出漏掉文案的图标按钮（WARN）。

**② 一个图标只承担一个功能。** 历史条目里「播放」和「还原任务」曾经都是 `AudioLines`，
而 `AudioLines` 同时还是「文生音」类型徽标的图标——同一个字形在一屏里指三件事，谁也读不准。
现在拆开：播放 `Play` / `Pause`、还原任务 `History`、类型徽标 `AudioLines`。
v2.1.2：「移动分类」原本用 `MoreHorizontal`（与历史栏「更多操作」同一个字形、同一屏里指两件事），
换成 `FolderInput`（带箭头的文件夹）—— 菜单里列的是分类，图标要能读出「放进某个夹子」。

**③ 密集列表行的操作默认全部 hover 才显示。** 历史条目此前是「播放、复制常显，
还原 / 下载 / 删除 hover 才出」——同一行并存两种显隐规则。现在 5 个统一。

**④ 例外：「进行中」的操作行整体保持可见。** 正在播放的那一条，鼠标移开也保持 5 个操作可见
（且播放键变 `Pause`）。只让暂停键可见会让这一行显得断裂，还会丢掉「正在播放」的提示。
**音色卡片是同一件事（v2.1.2）**：试听期间整排四个操作保持可见、日期退场、播放键变成**停止**键；
播完 `onEnded` 清空播放态，鼠标不在卡上时整排随之收起。
⚠️ **卡片用「停止」`Square`，不是「暂停」`Pause`**：试听再点一下是**停掉**、不会续播，文案也一直
是「停止试听」—— 字形必须和文案说同一件事（历史条目那边保留 `Pause`，因为那里点了还能接着播，
两边各自都是对的）。
⚠️ **播放态不叠底色块**：状态由「强调色 + 停止字形 + 整排保持可见」三件事表达就够了；先前那版
`bg-accent-soft` 是在 24px 小图标里多铺一块面，被判「不够简洁」后去掉。
⚠️ **「正在生成样本」（转圈、`disabled`）与「正在播放」是两个状态，不要共用一个 flag** ——
早先合成一结束就把 id 清了，于是播放期间卡片根本不知道自己在播，整排跟着鼠标一起消失。
实测（`state-check.mjs`）：点击后 `paused:false`（真的在播）、整排 `opacity:1`、日期 `opacity:0`、
按钮 `aria-label="停止试听"`、图标由 Play 的 `path` 变成 Square 的 `rect`、底色始终透明；
再点一次回到静止态；派发 `ended` 后四项同样回到静止态。**要验这条必须派发给「真的在放的那个」
`<audio>`**——页面里不止一个，派给第一个等于什么都没测。
⚠️ **整排的显隐判据是 `group-hover` + `group-has-[:focus-visible]`，绝不能用 `group-focus-within`**
（v2.1.2）：鼠标点过的按钮会长期持有 DOM 焦点，`focus-within` 于是把整排**永久**点亮 ——
实测：指针已移出卡片（hover=0）、音频已 `ended`，整排 `opacity` 仍是 **1**；换成 `:focus-visible`
后同一时刻是 **0**，而键盘 Tab 进来时照样是 **1**（焦点在按钮上、`:focus-visible` 成立）。
**这条的探针也必须换**：用 `element.click()` 测它永远绿——合成点击**不转移焦点**，
我第一版就是这么绿的；必须用 `Input.dispatchMouseEvent` 真点，并同时读 `document.activeElement`
与 `element.matches(':focus-within')`。历史条目（`LeftPane`）同步补上
`group-focus-visible` + `group-has-[:focus-visible]`：它原先根本没有 focus 那条臂，
键盘 Tab 进来时 5 个操作是「焦点可见、视觉不可见」的。
⚠️ 量「Tab 后整排出现」要**等过渡结束**（`duration-100`，等 320ms）：60ms 时读到 **0.92**，
那是过渡本身，不是最终值 —— 与 §9.2-8「不要在动画中途取样」同一条。

**⑤ 用 `Tooltip` 包**绝对定位**的元素时，定位类必须挪到外层容器。**
`Tooltip` 的 wrapper 自带 `relative`，而 `absolute` / `relative` 谁生效由 Tailwind 的生成
顺序决定（`relative` 在后），所以把 `absolute` 留在按钮上会**直接失效**：

```tsx
<span className="absolute right-2.5 top-1/2 -translate-y-1/2 flex">
  <Tooltip label="显示"><button …/></Tooltip>
</span>
```

外层那个 `flex` **不能省**：少了它，外层是行内级，高度会被行盒的 strut 撑大
（16px 图标撑成 22px），`-translate-y-1/2` 就按 22px 算，视觉上偏高约 3px。
（弹窗关闭键那种块级 `div` 外层不需要。）

**⑥ 判定与实测**：本仓库共 7 处图标按钮补上文案（历史条目 5 个 + 弹窗关闭 + 设置中心
显示/隐藏 + 音频播放键 + 两个录音圆钮 + Chip 的修改/删除 + 菜单确认添加）。
生产构建实测：眼睛按钮右内边距 10px、垂直居中偏差 0px；弹窗关闭键内边距不变；
录音圆钮仍为 72×72 / 64×64 正圆；历史条目 5 个操作静止态 `opacity: 0`、
hover 全为 1、播放中取消 hover 仍为 1；5 条文案均未被侧栏滚动容器裁切。

**⑦ hover 文案一律朝上（`Tooltip` 的默认 `side`），不要写 `side="bottom"`。**
指针就停在那个 24px 图标上，朝下的文案正好落在指针所在的高度带里（视觉上像被鼠标压住），
而小图标按钮又常常贴在卡片下缘、下方紧跟着下一行卡片。
实测（`CSS.forcePseudoState` 强制 **wrapper** 的 `:hover`，不是强制按钮自己的——`group/tt`
长在 wrapper 上）：音色卡片 4 个操作（试听播放 / 修改名称 / 移动分类 / 删除）的文案框都是
26px 高、底边落在按钮顶边之上 **6px**，即整块在指针上方。
**需要朝下的只有贴着窗口上缘的按钮**（`App.tsx` 的收起/展开侧栏，`side="bottom" align="end"`），
那里朝上会被窗口边缘切掉。

### 5.10 装饰色族与词汇轮播（v4.1 新增）

欢迎页主文案里那个轮播的词有 **7 种颜色**，而且整列会向上翻转。这一节同时管两件事：
颜色从哪来（一）、翻转怎么做（二）。

#### 一、装饰色族

7 个值**不属于语义色族**，是单独一套 `--hero-1..7`。这不是偏好，是规范推导出来的结果：

- §5.12-13 禁止装饰借用语义色（success / danger / warning / accent-2 必须表达真实状态）
- 去掉语义色后，合法可当文字色的 token 只剩 `accent` 与 `accent-2-text` 两个
- 要 7 个不同颜色，只能新建一族

| 色相 | 浅色 | 暗色 | 名称 |
|---|---|---|---|
| 225° | `#1F54F6` | `#6F92F9` | 克莱因蓝（品牌） |
| 186° | `#07717D` | `#0AA6B7` | 青 |
| 128° | `#0A7718` | `#0EAE23` | 绿 |
| 66° | `#626C03` | `#909F04` | 金黄 |
| 22° | `#AF4507` | `#F66D1E` | 爱马仕橙（品牌，有意与 `--accent-2` 同色相） |
| 330° | `#C3166C` | `#EE66AA` | 品红 |
| 275° | `#942AE1` | `#BD7AEC` | 紫罗兰 |

上表是色族的**身份**：这 7 个色相各是什么。**它不含「哪个词用哪个色」**——
token 的编号跟着**词序**走（`--hero-N` = 第 N 个词的颜色），配给哪个词按相邻色差最大化排过：

| token | 词 | 色相 | token | 词 | 色相 |
|---|---|---|---|---|---|
| `--hero-1` | 创造 | 225° 蓝 | `--hero-5` | 朗诵 | 22° 橙 |
| `--hero-2` | 克隆 | 128° 绿 | `--hero-6` | 识别 | 275° 紫 |
| `--hero-3` | 生成 | 330° 品红 | `--hero-7` | 模仿 | 66° 金黄 |
| `--hero-4` | 演绎 | 186° 青 | | | |

即**词序上的色相序列是 225 → 128 → 330 → 186 → 22 → 275 → 66**。
拿它跟上头那张色族身份表（按色相排的）对一下就能看出：配给顺序是**有意打乱**的，
理由见下面条款 5。

**硬性条款**

1. **明暗两套各 7 个值，一个都不能少。** 只定义浅色，暗色主题会静默回落到继承值
   （`design:check` 会报 `--hero-N 缺失`）。
2. **取值必须求解，不能挑。** 判据与 §5.3 一致：在「常态 / `--surface-hover` /
   `--surface-active` / `--accent-soft`」四种底里**最差的那个**上 ≥ 4.5:1。
   只按常态底求解会翻车——暗色主题的 `--surface-active` 比常态底**更亮**，
   按常态求解出来的 7 个值在它上面只有 **4.37:1**（实测）。
3. **七个值要落在同一个对比度带里**，目标是「分量齐平」，不是「都过线就行」：
   不能让某个词刚好 4.5、另一个 9.0 刺眼。现为浅色 5.54-5.58 / 暗色 5.76-5.81（常态底），
   最差底 4.70-4.74。
4. **色相要推离语义色。** 与 success(150°) / warning(40°) / danger(357°) 的色相差都在
   22° 以上；唯独品牌橙（22°）是有意与 `--accent-2` 同色相——这个产品的品牌就是蓝+橙，
   欢迎页是最该露出品牌的地方。
5. **排列顺序本身是设计决定，不是实现细节。** 轮播是**连续**展示这些色的，所以
   「相邻两个色的差别有多大」直接决定了它是「每翻一次换了个颜色」还是「沿色环走了一圈」。
   第一版按色相降序排（225→186→128→66→22→330→275），视觉上就是一道彩虹渐变——
   曾经翻到「生成→演绎」和「模仿→创造」时几乎看不出换了色。
   现按**相邻色差最大化**重排（判据是 CIE Lab ΔE，含 模仿→创造 这个首尾环），
   最差相邻 ΔE 从 **30.0 提到 88.8**（穷举 720 个排列取最优；
   把「创造」钉在品牌蓝上不损失分数，约束前后的最优解同分）。
   **改这 7 个色的排列前必须重跑这个判据**，不要凭色相角度差排——明度差也是色差，
   按角度排会把「金黄 vs 橙」这种明度相近的排在一起。
6. **只做装饰。** 这两族 token 不许拿去表达任何状态。

#### 二、词汇轮播动效

- **机制是「整列上移一格」**，不是逐个淡入淡出。7 个词 + 1 个首词克隆排在一条轨道上，
  每格高 `--reel-item-h`（= `text-3xl` 的行高 2.25rem）。换词 = 轨道 `translateY`
  前进一格，600ms `cubic-bezier(0.22, 1, 0.36, 1)`。
- **末尾必须克隆第一个词。** 否则从「模仿」回到「创造」时，轨道会当着用户的面倒卷 7 格。
- **克隆帧的停留时间要补偿掉。** 克隆让首个词连续出现两次；不补偿的话「创造」停留
  2.58s 而其余各 1.94s，每轮顿一下。现用 `TransitionEvent.elapsedTime` 把滑块耗时从
  下一次停留里减掉，实测各词停留 **1968 / 1964 / 1954 / 1956ms**。
- **`translateY` 不能用百分比。** 百分比相对**轨道自身高度**（8 格 = 288px）解析，
  `-100%` 会把整列甩出屏幕 8 格、一个词都露不出来。要按格高相乘：
  `translateY(calc(var(--reel-item-h) * -N))`。
- **槽位要 `overflow:hidden` + `vertical-align:bottom`。** `overflow:hidden` 的
  inline-block 基线取自底边，底对齐才能与两侧正文同基线（实测基线差 **0px**）。
  少了 `vertical-align` 会静默上浮约 4px。
- **所有词必须等宽。** 7 个词都是两个汉字，槽位不变宽，句子就不会在动画中重排
  （实测 h1 宽度恒定 297px）。换成长度不等的词就会抖。
- **标题的可读名要单独给。** 轮播整体 `aria-hidden`，`<h1>` 上用 `aria-label` 拼出
  「今天想X什么声音？」——否则读屏会把 7 个词连成一串念出来。
  **不要加 `aria-live`**，那会每 2 秒打断用户一次。
- **`prefers-reduced-motion: reduce` 时整个停住，而不是「只关掉过渡」。** 每 2 秒瞬移
  一次仍然是在持续夺走注意力。实测：开启该系统偏好后 5.2 秒内轨道 transform 不变。

### 5.11 文本输入区的指针（v4.3.4 新增）

浏览器自带的 I 形光标是一根 1px 细线。在这个界面上它读起来就是「白色的什么都没有」——
用户的原话是「编辑指针经常看不见」。所以**文本框里的指针改成设计的一部分**：
主题色、加粗、加高的竖条。

| 项 | 取值 |
| --- | --- |
| 形状 | 3×20 的圆角竖条（rx 1.5）+ 1px 描边，画布 9×24 |
| 屏幕尺寸 | 约 **4px × 21px**（原生约 1×16） |
| 热点 | `4 12`，即竖条正中 |
| 填色 | **该主题的 `--accent`**：浅 `#002FA7`（克莱因蓝）、暗 `#FF9A5C`（爱马仕橙） |
| 描边 | 浅色 **白**、暗色 **画布黑 `#0A0A0B`** |
| 作用范围 | `textarea` / `[contenteditable]` / 文本类 `input` |
| 降级 | 末尾必须留 `text` |

三条判据，每条都有一个「看起来更简单」的错答案：

- **为什么是 SVG，不是 PNG**：指针图片按 CSS px 给尺寸、再由显示器 DPI 缩放，所以 PNG
  在 125% / 150% 缩放的笔记本上必然发虚。SVG 按真实倍率栅格化。9×24 也远在 Chromium
  的 128×128 上限之内 —— **超过上限的指针图片会被静默忽略**，你只会看到原生指针，
  且没有任何报错。
- **描边的颜色是照着「文字」选的，不是照着底**：指针画在**字形上面**，而字形与底的明暗
  关系随主题翻转，所以浅色主题（深色字）描边用白、暗色主题（浅色字）描边用画布黑。
  也正因如此，描边落在**底**上等于不存在（浅蓝底上的白、近黑底上的黑都融进去），
  它只在压到字上时才起作用 —— **它不会让竖条看起来变粗**。
- **填色是 `--accent`，不是 `--accent-strong`**：暗色的近黑底上，深一点的橙反而是更弱的
  信号，而指针必须是光标下面最亮的东西。

- **⚠️ 作用范围那份清单与 `glassLight.ts` 的 `TEXT_ENTRY` 是同一个概念**：拿到自定义指针的
  字段，就不该同时被指针灯照亮（灯最亮处正落在光标处，正好盖住这个指针对不对）。
  CSS 读不到 TS 数组，而每次 `pointermove` 读一次计算样式正是 `glassLight.ts` 竭力避免的
  开销，所以两份清单只能各写一次 —— **改一处就要改另一处**，验收脚本两边都取样
  （§9.2-19）
- **⚠️ 这个取值必须写两遍，而且只许颜色不同**：data URI **不能插值 `var()`**，指针图片也
  **继承不到 `currentColor`**，所以「按主题换色」只能把整张 SVG 复制一份。这是本仓库
  **唯一一处必须复制的设计取值**，因此也是唯一一处需要门禁盯着的：`design:check` 把两边
  的颜色抹掉后逐字比较，并断言填色**等于该主题的 `--accent`**、热点落在竖条内、
  末尾留着 `text` 降级项。
  **改了几何却忘了改另一边 ⇒ 两个主题一个粗一个细**，而这类差异**没有任何测量项会去问**
  （同 §10.2 的「下拉在哪」）。三条断言都实测过「破坏之后会不会红」，不是写完就算

### 5.12 反模式（出现即打回）

1. ❌ 任意值字号 `text-[Npx]` —— 只用 5 个原生类
2. ❌ 任意值圆角 `rounded-[Npx]` —— 只用 3 个命名类
3. ❌ 字重 700
4. ❌ 语义色直接当文字色（必须用 `-text` 变体）
5. ❌ 用 1px 字号差表达层级（层级 = 尺寸 + 字重 + 颜色 三者合力）
6. ❌ 页面标题 ≤ 导航项尺寸（或页面标题无 icon）
7. ❌ 同一个角色在不同页面用不同尺寸
8. ❌ 标签与它的辅助说明同字号
9. ❌ 内联色值（只能用 token）
10. ❌ emoji 图标
11. ❌ 每视图超过 1 个主 CTA
12. ❌ **交互控件的「标签文字」出现 12px** —— 按钮 / 页签 / 分段控件 / pill 一律 body(14px)。
    12px 只留给 caption（辅助说明，含 `DropdownMenu` 的 `heading` 菜单标题）与头像首字（本次两处违规：历史筛选页签、当前音色 pill）。
    **判据是「这段文字是不是在标识一个操作」，不是「它所在的那行可不可点」。**
    历史记录条目整行可点（`role="button"`），但行内正文标识的是**哪条记录**、不是某个动作，
    属于内容预览，因此 12px 合法（v4.1）。反过来，把按钮/页签自己的文字做成 12px 仍然打回
13. ❌ **装饰性标识借用语义调色板** —— 语义色（success / danger / warning / accent-2）
    必须表达真实状态。头像按哈希轮转穿 4 个语义色就是反例：绿色/琥珀色凭空暗示
    「成功/警告」，橙色还违反 §10.3 的品牌约定（已统一为单一品牌主色）。
    **装饰要用色就新建一族**，做法见 §5.10-一
14. ❌ **同类控件跨组件取值不一致** —— 如分段控件与历史筛选页签的未选中态都必须是
    `text-ink-2`。**判定前先把实际 class 打出来**：聚合统计只能说明「有几处不同」，
    说明不了「为什么不同」（我曾在只看三元组时把 4 类档位外用法误判成有意设计）
15. ❌ **一个图标承担两个不同功能** —— 播放与「还原任务」曾共用 `AudioLines`，
    而它同时还是「文生音」徽标的图标。图标与功能的对应必须**一对一**（§5.9-2）
16. ❌ **无文字的图标按钮没有 hover 文案** —— 只有 `aria-label` 不算：那是给屏幕阅读器的，
    肉眼看不到。必须用 `<Tooltip label>` 包一层（§5.9-1）
17. ❌ **固定位置、固定尺寸的装饰形状重复出现** —— 一屏 15 张音色卡（列宽 247.6px），
    重复 15 次之后读到的是**底纹/图案列**，不再是「这张卡的身份」。
    音色卡片的装饰前后被否掉三版（首字圆头像 → 左缘半圆 → 首字水印）都是死在这条上。
    **装饰的差异要来自内容**（该条自己的波形），做法与实测见 §5.13

### 5.13 音色卡片的水印波形（v2.1.2 新增）

克隆音色的音色卡片，在名称与日期之下画一层**该角色样本自己的峰值包络**：34 根 2px 圆头
竖条，以卡片中线为中心上下对称展开（`h-12`），整层 `.voice-card-wave`
（`opacity: var(--wave-mark-opacity)`，见下），颜色 `bg-accent`。

#### 为什么是「内容」而不是「形状」
这条装饰前后被否掉三版：首字圆圈头像 → 左缘半圆 → 首字水印。三版的共同死因不是「不好看」，
是**可重复**：一屏 15 张卡，任何固定位置、固定尺寸的形状重复 15 次之后，眼睛读到的是底纹，
不是身份（实测旧半圆 15 张卡的 x 与尺寸完全相同）。
波形天然不可重复——它由**该角色自己的样本**决定，一屏看过去是「每张卡里都有一段自己的声音」，
而不是「每张卡某个角落多了个同样的记号」。它同时用掉了卡片本来就空着的横向留白，且左右对称，
读起来是「标题落在自己的声音上」，不是两个并排的物件。

#### 数据从哪来（不要在 UI 层解码音频）
- `cmds/voices.rs` 的 `waveform_peaks()`：认 16-bit PCM WAV（本项目录音器写出的格式），
  按 chunk 遍历找 `fmt `/`data`，把样本切成 34 段、每段取 **max |sample|**、按全局峰值归一
  到 0~1、保留两位小数。读不出来（其它位深、截断、纯静音）返回 `None`
- 峰值写在 **`config/voices/list.json` 的 meta** 上（保存时由 `voices_save_voice` 算），
  因为音色库只读 `list.json` 渲染；放进 profile 就意味着列表要逐个打开 profile 才能画
- 旧角色由 `voices_load_list` **一次性回填**（读不出样本的写成 `null`，避免每次加载重算）；
  前端 `waveform?: number[] | null`，缺失或为 `null` 就不画这层
- ⚠️ **禁止在列表渲染时现解码音频**：15 段 WAV 每次进页面解一遍会明显卡，且这是纯派生数据，
  没有理由让 UI 线程承担
- 复制出来的两个角色**波形相同是对的**：样本相同，包络就该相同

#### 强度是「按主题给的 token」，不是 Tailwind 档位
取值在 `index.css` 的 `--wave-mark-opacity`：**亮色 0.05 / 暗色 0.10**，由 `.voice-card-wave`
消费。**两个主题故意不共用同一个数**：
- 亮色卡底本来就亮，10% 的**冷色**墨（实测 `rgb(212,225,246)`，Δ20 级）读起来是一块灰痕，
  用户判定「太重」；同一时刻暗色同值却被判「很完美」。降到 5% 后实测 `rgb(223,234,249)`（Δ11 级）
- 暗色不能跟着降：那里的墨是**提亮**的暖橙，在近黑卡上读作「被照亮」而不是「脏」，
  降到 5% 就没有了。**同一个数字在两个主题里读作两种东西，所以它不是审美参数**

#### 强度上限由 12px 日期顶住（实测）
画在文字下面一层的东西必须核算文字的**最差底**。实测（CDP 取渲染像素 + WCAG 相对亮度）：

| 主题 | `--wave-mark-opacity` | 卡底 | 水印墨 | 名称 `--text-1` | 日期 `--text-3`（12px） |
|---|---|---|---|---|---|
| 亮色 | 0.05 | `rgb(235,245,254)` | `rgb(223,234,249)` | 15.53 → **14.10** | 5.02 → **4.78** |
| 暗色 | 0.10 | `rgb(39,39,43)` | `rgb(61,51,47)` | 12.71 → **10.47** | 5.97 → **5.20** |

- 名称怎么压都安全；**卡住上限的是 12px 的日期**——它在亮色静止底上只剩 5.02:1 的缓冲
- 亮色的墨加到 `opacity-15` 时实测 `rgb(200,215,241)`，日期掉到 **4.43:1，破 AA**。
  所以亮色的上限是 10%，再深必须先给 `--text-3` 让余量
- 暗色反而更宽（5.20）：水印是提亮的暖橙，浅色文字在更亮的底上仍保住 10.47 / 5.20

#### 门禁口径
这层是「`--accent` @5%（亮）/ 10%（暗）叠在卡片上」，都比 `design:check` 底模型里已建模的最差底
（`--accent-soft`：亮 9% / 暗 14% 叠卡片）更淡，**因此不需要新增底模型条目**。
⚠️ 反过来说：**哪天把透明度调高到超过 `--accent-soft`，就必须先把它加进 `design:check`
的底模型**（§10.2.4「门禁建模了什么，就只保证什么」）。

### 5.14 采集入口：并列两个方式，代价贴在各自下面（v2.1.2 新增）

「提交音色样本」原先是一组分段控件（录音 / 上传文件）+ 两个互斥分支，付三份代价：选哪边要多点
一次；两种方式的说明各写一份、各自维护；**拖放区只在 `upload` 分支里存在**，于是「拖文件进来」
看起来只属于其中一边。现在合成**一个投递面**（`rounded-md` + 虚线边），两个 64px 圆钮并排居中：

| | 录音 | 上传文件 |
|---|---|---|
| 圆钮 | **同一套**：`bg-accent-soft text-accent` + `Mic 24` | **同一套**：同上 + `Upload 24` |
| 标签 | 兼作状态：开始录音 / 正在录音 00:12 / 已录制 00:24 | 固定「上传文件」 |
| 说明 | 环境噪声会被一起刻进音色 | 已有干净录音时更稳 |

⚠️ **二选一不许有层级**：两个圆钮的尺寸 / 图标色 / 底色 / hover 全部来自 `SAMPLE_DISC` +
`SAMPLE_DISC_IDLE` 两个常量，实测**逐项相等**（64×64、`9999px`、`rgba(0,47,167,0.09)`、
图标 `rgb(0,47,167)`、0px 边框、svg 24）。唯一的例外是「正在录音」这个**状态**
（`bg-danger` + `recording-pulse` + **图标换 `Square`**）—— **状态与层级是两件事：状态允许变，
层级不允许**。
⚠️ **进行中的按钮，字形要换成它此刻的语义**：录音中按下去是「停止」，所以圆里必须是停止符、
不是话筒 —— 与音色卡片试听的停止键同一个字形（§5.9-2 一图标一功能）。
实测（`record-icon.mjs`，真鼠标点下去）：`aria-label` 开始录音 → 停止录音、图标
`path+path+rect`(Mic) → `rect`(Square)、两者都是 24px、底色 `rgba(0,47,167,0.09)` →
`rgb(218,55,51)`(`--danger`)、图标色 → `rgb(255,255,255)`。
底色**绝不能写成「基础类 + 覆盖类」**：两个 `bg-*` 谁赢由 Tailwind 的生成顺序决定，不由类名
先后决定，所以录音态是「状态各给一份底色」，不是覆盖。

**重量是量出来的，不是感觉**（`disc-check.mjs` 读计算样式 + `png.mjs` 读渲染像素）：

| 圆钮 | 渲染底色 | 与卡底的亮度差 | 图标对比度 |
|---|---|---|---|
| 旧左（实心品牌色） | `rgb(0,47,167)` | **−198 级** ✗ 过重 | — |
| 旧右（`--surface-2` + 描边） | 与卡底**同一个 token** | **0 级** ✗ 只剩一条 1px 线 | — |
| 备选（`--surface-1` 白面） | `rgb(248,251,255)` | **+7 级** ✗ 低于 8 级可见线 | — |
| **现方案（`--accent-soft`）** | 亮 `rgb(215,227,246)` / 暗 `rgb(69,51,42)` | 亮 **−18** / 暗 **+14**（通道跨度 21 / 29） | 亮 **8.25:1** / 暗 **5.70:1** |

旧右侧为什么轻到看不见：`.mat-card` 自己就是 `--surface-2`，圆钮也用 `--surface-2` ⇒
填充与底**同色**，那个圆实际只有一条描边。**给一个面加材质前，先确认它和它所处的面不是
同一个 token。**

**提示怎么写（本节要点）**：把**代价贴在它所属的那个选择下面**，不要写成一句需要用户自己
往两边映射的对比句；各自那一行写完，再补一条**共享**的能力说明（格式 / 大小 / 也能拖进来）。
措辞用**具体画面**而不是形容词 ——「环境噪声会被一起刻进音色」比「效果差」更能让人当场做决定。
两条说明**同字号（12px caption）同颜色（`text-ink-3`）**，不要给录音那条加重或加警示色：
那是在用装饰替用户做判断，而这个判断本来就该由「代价 + 自己的录音环境」得出。

实测（`sample-verify.mjs`）：
- 两列（各 160px，间距 64px）**基线对齐**：圆钮 y=217 / 直径 64、标签 y=289、说明 y=349，两边一字不差
- 说明与共享行字号 12px；投递面 `rounded-md`(12px) + `border-dashed`
- 拖入高亮：静止 `rgba(15,35,80,0.16)` → 拖入 `rgb(0,47,167)` → 拖离复原。**必须等过渡结束再读**：
  120ms 时读到的是过渡中途的 `rgba(10,39,109,0.22)`（与 §9.2-8 同一条）
- 采集卡高 **200 → 295**：多出来的是两个入口 + 两句代价，不是留白
- 录音时上传键 `disabled`；波形位**常驻 24px**，所以录音中下面那句说明不会跳
- 两个圆钮都带 `Tooltip`（上传那个的标签在按钮**外面**，按钮本身仍是图标按钮，按 §5.9-1 要文案）

### 5.15 文生音：先问「写到哪里」，再问「怎么写」（v2.1.2 新增）

这一页的「乱」来自把**两个目的地**的控件放进了同一排：

| 目的地 | 谁写它 | 产物 |
|---|---|---|
| `userPrompt`（风格） | 风格 chips / 自然语言描述 / 导演讲绎 | 一条 user-content |
| 朗读文本 `text` | 手打 / 开场标签 / 内嵌标签 | 要念的正文 |

`userPrompt` 一次只发一条（`TextToSpeech.tsx:299` 的注释），所以风格侧的三种写法**互斥**；
而开场/内嵌标签是**往正文里插字**（`setText`：开场前置或并进开头括号、内嵌插在光标处），
它们**彼此不冲突，也不与风格互斥**。原先这三者被画成同一排长得一样的按钮 ⇒ 用户只能以为
它们是一类 —— 这是"层级多/显得乱"最实在的来源。

**规则：一个触发器必须和它写的东西在同一张卡里。**

- 「风格控制」留在语音设置卡（它写 `userPrompt`）
- 「开场标签 / 内嵌标签」留在**朗读文本卡**、紧挨正文输入框（它们写 `text`）
- 名字要短且准：在正文卡里叫「开场标签 / 内嵌标签」，不再叫「开场风格标签 / 内嵌音频标签」

**方式排（第 2 步）**：一级（音频标签控制 / 自然语言控制）与二级（一段话描述 / 导演演绎）合并成
**一排三选一** —— `标签方式` / `自由描述` / `导演演绎`，各自 14px 图标（`Tag` / `FileText` / `Drama`，
图标随伴读的 14px 文字取档，§5.8 规则一）。三者互斥，因为都写同一条 user-content。一排下面
**只显示当前方式那一条**说明（"用现成标签，最快、结果最稳" / "写一段话，最自由；可套示例或让
AI 帮写" / "按角色 / 场景 / 指导三要素描述，表演意图最明确"）—— 不写成三行对比句让人自己映射
（同 §5.14 的做法）。

- **标签方式**：风格 chips **常显**（原先要点一次「风格控制」才展开）；不出现 示例 / AI
  （标签本身就够具体，这是有意的不对称）
- **自由描述 / 导演演绎**：输入区（+ 示例 + AI 生成风格描述）直接铺在设置卡里，**不再套一层
  `.mat-card`**（卡中卡清零，三种方式都是"设置卡里直接放输入区"）
- **开场/内嵌标签只在标签方式下出现**（用户明确要求）：由 `ttsMode === 'tags' &&` 门控；
  切方式时展开的标签面板自动收起（`setStyleMethod` 里 `setTagPanel(null)`）
- 展开状态 `openPanel`（`'style' | 'opening' | 'inline'`）**已删除**："显示什么"由所选方式直接决定；
  只剩 `tagPanel`（`'opening' | 'inline'`）。**历史落盘字段名仍叫 `openPanel`**（schema 不改），
  读时忽略老值 `'style'`

实测：插入语义一字未改（`.review/tts-insert.mjs`）—— 点「开心」→ 正文 `(开心)`、同一标签重复点击
幂等；打字 `ABCD` 后点「吸气」→ `ABCD（吸气）`（光标处）。三种方式实测（`.review/tts-ways.mjs`，
1200×800）：卡片高度 **标签方式 166+319**、**自由描述 268+277**、**导演演绎 404+277**（都是"设置卡 +
正文卡"两张，无卡中卡）；三选一三个图标实测都是 **14×14**；自由描述 / 导演演绎下
「开场/内嵌标签」实测**不存在**；面板生命周期"点开 → 切走 → 切回" = `true / false / false` ✓。

**第 3 步（已收口）**：

- **示例 chip 不再覆盖正文**：正文为空 → 填入示例（示例的意义所在）；正文已有内容 → 保留并提示
  「朗读文本已有内容，示例只填入了风格描述」。**风格描述两种情况下都写入**。实测
  （`.review/tts-step3.mjs` / `tts-step3b.mjs`）：正文 `MINE` 保持不动 ✓、风格描述 0→147 字 ✓、
  提示出现 ✓。判据：**任何"顺手填一下"的操作都不许无声替换用户输入**。
- **标签 chip 改成真控件**：chip 本体从 `<span onClick>` 改为 `<button>`（Tab 可达、Enter/Space
  可插），删除角标是它的**兄弟** `<button>`（按钮套按钮是非法 HTML），角标用
  `Tooltip label="删除标签"` 且 `group-has-[:focus-visible]:opacity-100`（键盘聚焦也现身，
  不必鼠标悬停）。实测面板内可聚焦元素 56 个、文字按钮 48 个。
- **一致性收口**：① 「清空」一律 `w-6 h-6 rounded-sm` + `Trash2 size={12}`（实测三处都是
  24×24 / 12×12）② 字数一律在多行文本域右下角，用 `h-6 flex items-center` 让文字的**中心
  距各自底边都是 13px**（实测一致）③ 三个多行文本域都 `placeholder:text-xs`（实测 12px）

### 10.2 三级材质（液态玻璃，v4.3）

| 层 | 类名 | 表面（亮 / 暗） | blur | 边 | 圆角 |
|---|---|---|---|---|---|
| M1 页面面板 | `.mat-panel` | 白 `0.58` / 灰 `0.55` | 28px + 160% | 渐变描边 + 顶部镜面 | 16px |
| M2 卡片 | `.mat-card` | **淡蓝 `0.56`** / 灰 `0.50` | **无**（理由见下） | 同上 + 指针灯光 | 12px |
| M3 弹层 | `.mat-overlay` | 白 `0.86` / 灰 `0.84` | 40px + 160% | 渐变描边 + 顶部镜面 | 16px |

**亮色 M2 为什么是淡蓝而不是白。** 白色表面上**没有玻璃可以成立的地方**：一张半透明白卡片
叠在近白面板上，唯一的差别是亮度，能动的只剩场景渗透——而两层半透明相叠会把压缩**相乘**
（`(1-0.56)×(1-0.58) = 18%`），实测淡蓝卡片之前那张白卡的红通道在整个视口里只差约
**1.5 级**，看不见。给卡片一个自己的淡蓝，这一层才有**颜色**，而颜色正是玻璃真正被读到的
东西——这也正是暗色一直能成立的原因：那里表面是灰的，场景的橙和蓝能透出来。
现取值 `rgba(226, 240, 254, 0.56)`，叠在面板上的合成值是 `rgb(236, 245, 254)`，
与面板 `rgb(250, 251, 253)` 相差约 14 级——是「淡淡的蓝」，不是一块蓝色。

**代价如实记账：卡片变暗 = 深色文字掉对比度。** 这一个改动把亮色三个最边缘的 token 全部
压破，各压深一档才过：`--success-text` `4.43 → 4.73`、`--warning-text` `4.54 → 4.87`、
`--accent-2-text` `4.56 → 4.77`（同一个浅蓝画布、同一片场景网格上的最差值）。

**M2 为什么不加 blur。** 卡片永远坐在 `.mat-panel` / `.mat-overlay` **里面**，而那个面板
已经把场景模糊过了 —— 卡片自己的背底本来就是平滑的，再模糊一次视觉上买不到东西，却要多付
一整块 render surface。v4 写这条时给的理由是「性能红线」，**那是个错理由**：真实理由是这个。
想通之后 M2 反而可以做成最透的一层（`0.50`），因为它透出来的底是干净的。

**同屏 `backdrop-filter` ≤ 3**（实测 3 / 148 个元素）。新增模糊之前先问一句
「它的背底是不是已经被上游模糊过了」。

#### 10.2.1 场景：模糊必须有东西可模糊

**`backdrop-filter` 在平底上是数学空操作。** 这是 v4.2 之前「怎么调都不像玻璃」的真正根因：
`body` 只有一层 `radial-gradient(rgba(232,244,253,0.85))`，而 `#E8F4FD` 与画布 `#EDF3FA`
只差 1–2 级 —— 整块背底的亮度变化约 2%，模糊它和不模糊它看上去一模一样。
调大模糊半径之所以毫无变化，也是因为这个。

现 `--bg-scene` = **画布 + 三个大半径径向渐变**：
亮色是白色高光 + 极淡蓝/暖对位（相对画布最大通道偏移 **R8.7**）；
暗色是暖橙 `0.13` + 蓝 `0.10` + 紫 `0.06`（相对画布最大通道偏移 **R24.6**）。
三条硬性要求：

1. **必须有结构**：单通道最大跨度 ≥ 8 级，否则 `design:check` 直接失败。判据用
   **通道跨度**而不是亮度跨度 —— 暗色场景把近黑画布从亮度 0.003 抬到 0.009（等于没动），
   但红通道动了 **24 级**，而模糊抹平的正是这个；只看亮度会把暗色误判成「没有结构」
2. **场景取值由门禁从 CSS 解析，不许在门禁里抄一份**：`design-check.mjs` 读 `--bg-scene`，
   在 9×7 网格上合成出「面板 / 卡片」各自的一整片底色，再取最差。抄一份必然漂移，
   而按旧场景判定比不判定更糟 —— 它给的是假阴性
3. **降表面不透明度 = 把一部分文字预算让给背底。** 这是 v4.3 的代价，账簿要记清楚：
   亮色 `--accent-2-text` 从 `#C2410C` 压深到 `#B93D0B`（4.39 → 4.77:1，同色相下一档），
   暗色 `--text-3` 从 `0.58` 抬到 `0.60`（4.49 → 达标）。**改 `--surface-*` 的 alpha
   必须重跑 `design:check`**，它会用新场景重算全部配对

#### 10.2.2 边、光与指针灯（v4.3.1）

- **渐变描边** `--glass-edge`，走 padding-box 遮罩法，由 `::after` 承载（`inset:0` +
  `padding:1px` + `mask-composite: exclude`）—— 这是唯一能同时保住 `border-radius` 和不加
  DOM 的做法。暗色的 `--inset-hi` 原先只有 `rgba(255,255,255,0.04)`：4% 白压在近黑上
  等于不存在，**暗色主题此前根本没有玻璃边**。该 token 已删除，顶部高光并入描边第一档
- **顶部镜面** `--glass-sheen`，作为 `background-image` 的顶层（亮色 0.55 / 暗色 **0.022**）。
  三种材质共用同一套概念，谁都不许长出自己的配方。暗色从 0.055 降到 0.022 不是口味：
  实测 0.055 单独一项就把 `--accent-2-text` 压在 3.90:1（见 §9.2-16）
- **指针灯** `--glass-glow` + `--glass-light`，由 `::before` 承载，位置来自
  `services/glassLight.ts` 写的 `--glass-x` / `--glass-y`。**取代了 v4.3 的 hover 扫光** ——
  扫光是固定角度、固定路径的一条光带，每张卡片都一样，和鼠标在哪无关，所以读起来"机械"。
  光源应该在光**所在**的地方。
  - 它是 `inset:0` + `border-radius:inherit` 上的**背景**径向渐变，不是位移的浮层：
    这样永远出不了盒子，卡片不需要 `overflow: hidden`（卡片里会弹下拉与 Tooltip，必须能溢出）
  - 默认位置是 **`-9999px`（盒外）**，不是 50%：`--glass-light` 是固定半径，
    居中的默认值会在鼠标还没靠近时就把小卡片点亮
  - hover 用 `opacity` 门控（240ms 淡入）；未 hover 时浏览器**整个跳过绘制**
  - **只给 M2 / M3，不给 M1**。理由见下
- **灯的色相必须服从表面的色相**：亮色 **`#FFFFFF@0.55`**，暗色 **`#F37021@0.06`**。
  两个主题这盏灯**颜色不同，而且不再假装是同一个效果** —— 这个结论被推翻过两次，
  两次的推理都留在这里，因为错的那一半更值得记住。

  - **v4.3.2 的推理（错）**：白光只能提亮，可见度上限是表面**向上的余量**。
    亮色卡片合成到 `rgb(235,244,254)`，0.42 白光峰值 `rgb(243,249,254)` = **+8/+5/+0 级**，
    而蓝通道本就在 254，白光在那里无处可去。于是把灯改成暖白 `#FFF0DA@0.56`，
    峰值 **+12/−3/−20 级**，联合信号 2.5 倍 —— 算术全对，**但结论错了**。
    它只回答了「能拿到多少信号」，没回答「那个信号该不该出现在这里」。
    暖橙打在**淡蓝**卡上就是色相打架，一眼就能看出来。
  - **幸存的判据**：**灯的色相必须服从表面的色相**。暗色表面是中性灰（R=G=B），
    橙光没有可打架的对象，所以成立；亮色卡本身就是淡蓝，唯一能接受的是它**自己的**色相
    —— 而任何比卡片深的颜色都是**阴影**不是光。于是只剩一个选项：**白**。
  - **v4.3.3 的推理（也错，错法不同）**：蓝通道封顶在 254，所以「余量」就等于「天花板」，
    白光峰值理论极限只有 **+20/+11/+0 级**；0.42 只买到 +8/+5/+0。于是推出
    「在顶到天花板的通道里没有『含蓄』这个选项，灯只能把余量花光」，取到 **0.85**
    （实测 +17/+8/+0、欧氏距 19、片内落差 25）。**算术仍然全对，结论仍然错** ——
    用户读到的是一块**干扰视线的亮斑**。**花光天花板 ≠ 花光设计需要的那部分。**
  - **现在是 0.55**，实测 **+11/+5/+0**（欧氏距 **12**、片内落差 **12**），
    也就是「若隐若现」。它之所以付得起这个淡，是因为**灯已经不再承担 hover 反馈**了：
    那是 `--shadow-card → --shadow-lg` 的活，代价 **−46 级**，信号量高一个数量级。
    **灯是叠加在真实状态变化之上的装饰，所以可以很淡**；哪天它又要独自承担状态变化，
    正确的做法是把状态变化还给阴影，而不是把这个数调高
  - 加深卡片（约 +17/+11/+2）同样有效，但要把 **5 个语义 token 各再降一档**，回退了。
  - **暗色的灯被文字对比度硬顶在 0.06**：实测即使只升到 **0.075**，`--text-3` 也在
    `accent-soft@光心@卡片` 上掉到 **4.44:1**。这不是保守取值，是天花板。
    想把暗色的灯做强，必须先给文字 token 让出余量
- **⚠️ 文本输入区不能有指针光，而且只能靠「位置」排除，不能靠透明度**（v4.3.4）。
  灯是 `::before` 画在 `inset:0`，也就是**盖在元素内容之上**，而它最亮的地方**正是光标处**。
  在文本框上就是一块亮斑压住插入符和 I 形光标 —— 那是全应用唯一「指针自己的字形就是你
  正在瞄准的东西」的地方，用户一提就提到了（「鼠标的编辑指针都看不到了」）。
  - 实测：`--glass-x` 在光标处，而 `::before` 的 `opacity` **仍然是 1** —— 卡片确实还是
    hover 态。所以**调透明度根本表达不了这件事**，只能把 `--glass-x/-y` 放回盒外
    （`-9999px`，也就是那个本来就存在的「停到盒外」状态）
  - 实现在 `services/glassLight.ts` 的 `TEXT_ENTRY`：`textarea`、`[contenteditable]`、
    以及 `input:not([type=button|submit|reset|checkbox|radio|range|file|color])`。
    **判据是「浏览器在这里给不给 I 形光标」** —— 勾选框不需要保住光标
  - 命中后 `park` 并且 `last = null`：丢掉矩形缓存，回到卡片上要重新量。这也是让停用
    **持续生效**的关键 —— 在文本框里可以打字好几分钟而不再有任何 `pointermove`，
    期间不能让任何东西把它重新点亮
- **灯的半径必须相对元素，不能是死值**（v4.3.2）。渲染像素实测：`300px` 半径落在首页
  190×132 的卡片上会**盖满整张卡**，于是灯不再读作"跟着鼠标的光斑"，而读作"整张卡微微变了色"
  —— 四角与光心只差 11 级。现由 `services/glassLight.ts` 在进入元素时按
  **`min(主题上限, max(60px, 0.7 × 短边))`** 收窄：首页卡 92px，落差从 11 涨到 **20**。
  60px 下限是留给小浮层（125×26）的，否则径向渐变在边缘之前就没了。
  **主题 token 是上限而不是取值** —— fit 只缩不放，那个 token 才还有意义
- **亮表面用阴影读自己的边，不用描边；而且描边不能是渐变**（v4.3.3）。
  这条改了三版，三版都留在这里，因为每一版都是「上一个结论只对了一半」。

  - **第一版（错）**：亮色描边用白。暗色的卡片一直更好读，原因就是描边 ——
    `rgba(255,255,255,0.20)` 在近黑卡上是 **+43 级**；而白对近白卡最好也只有 +19，
    而且最强的那个 stop 落在**角**上（1px 斜线在角上只有约 50% 覆盖）。
    渲染像素实测：旧描边只有 **~9 级**，等于没有。
  - **第二版（也不对）**：换成深蓝**渐变** `rgba(15,35,80,0.16 → 0.26)`。
    强度到位了（−25 到 −55 级），但**渐变让四周在颜色和视觉粗细上都不一致**，
    于是读起来不是玻璃边，而是**一圈残缺的边框**。渐变本身就是要让四个方向不同 ——
    这在暗色里成立（受光的角最亮 = 光照），在亮色里只是让人看见「这圈线画歪了」。
  - **第三版（现在）**：亮色的边退回**单一扁平值** `rgba(15,35,80,0.08)`。
    **不渐变 ⇒ 四周必然均匀**，这是结构性保证，不需要靠测量去证明。
    而「这是一张卡片」的分量交给**阴影**：
    `--shadow-card` 承载静置的卡片感，`--shadow-lg` 承载 hover 上浮。
    实测卡下缘静置 **−28 级**、20px 内衰减完；hover **−46 级**、约 44px 衰减完。
  - **暗色继续用渐变描边**（那里它是 +43 级的受光边，渐变读作光照）。
    **这个不对称是故意的**：同一个概念（标出边界）用表面付得起的方向表达。
  - **判据用对比度比，不要用级别差**：直接比会误判（55 vs 41，看着像浅色过头）。
    这是**第四次**栽在「采样口径」上 —— 亮的底和暗的底，级别差根本不是同一个单位
- **阴影的「触达范围」也是规格，不只是深浅**（v4.3.3）。`box-shadow` 会在盒外画出
  `0 24px 64px` 那么远，所以**改阴影几何就等于改变它需要多少空间**。
  亮色 `--shadow-lg` 是 `0 16px 44px`（左右 44 / 上方 28 / 下方 60），
  暗色仍是 `0 24px 64px`（64 / 40 / 88）——**两个主题不共用 hover 阴影**。
  给滚动容器留位要按**触达更远的那个主题**留。另外 `--shadow-card` 只给
  **18px 侧面 / 24px 下方**：它被左侧栏自己滚动容器里的历史卡片用着，投得太远就是下一个被裁的
- **⚠️ 把 `:root` 里的 `var()` 派生 token 换成字面量，会连带改掉所有没重新声明的主题**：
  `--shadow-card: var(--shadow-sm)` 声明在 `:root`，而自定义属性的 `var()` 是
  **在声明它的那个元素上**解析的 —— 所以暗色只要覆盖 `--shadow-sm`，`--shadow-card`
  就自动跟着变。把它改成亮色的字面量后，暗色块没有重声明 ⇒ **暗色卡片拿到了蓝黑阴影**
  （实测卡下 `26/28/34`，蓝通道比红高 8，而暗色表面按规矩必须 R=G=B）。
  修法是暗色块里显式重声明一次。**看到 `:root` 有 `var()` 派生 token 时，
  先数清楚有几个主题块在覆盖它的来源**
- **描边不加指针灯**，尽管「一圈随鼠标游走的高光弧」是最显然的放法、而且完全不花文字对比度：
  实测重绘 `::after` 会逼着带 `backdrop-filter` 的面板**祖先**重新栅格化，约 **50ms/帧**，
  且与面积无关（125×26 的浮层和 796×110 的卡片一样贵；把灯的半径从 300px 缩到 120px
  毫无变化）。把面板的 `backdrop-filter` 关掉成本归零、把灯设为不绘制成本归零、
  只写自定义属性成本归零 —— 三组对照说明付钱的是**模糊**，不是灯。详见 §9.2-17
- **hover 反馈用"光与影"，不用位移**（v4.3.2）：首页三张功能卡原先是
  `transition-all duration-100 hover:-translate-y-0.5`，读起来像**卡片和它自己的内容脱开**——
  一段 100ms 的 transform 会经过小数偏移，标签与图标每帧都在新的次像素位置**重新栅格化**，
  而卡片自己的边最后才落定，于是文字像是从卡片底下滑出来。**抬升是阴影的概念**：
  现在位移取消，由 `hover:shadow-lg` 承担（亮色 `0 16px 44px` + 2px 接触层，
  静置是 `--shadow-card` 的 `0 6px 18px`；暗色 `0 24px 64px`），`transition` 也从 `all` 收窄到
  只剩 `box-shadow`（`all` 会把每一次无关的属性变化都拉进过渡）。
  这三张卡同时是**唯一**直接落在场景上、不在面板里的 `.mat-card`（`App.tsx:228` 的
  `<main>` 子节点），所以门禁里多了一个「裸卡片」基座
- **⚠️ `overflow-x-auto` 会把纵向一起裁掉,没有只裁一个轴的办法**（v4.3.3）。
  卡片那一行是 `flex ... overflow-x-auto px-6 py-1`，于是它成了滚动容器 ——
  而 `overflow-x` 不是 `visible` 时，`overflow-y: visible` 按规范会**计算成 `auto`**，
  **两个方向都裁**。`hover:shadow-lg` 在暗色是 `0 24px 64px`（左右各 64px、下方 88px），
  在亮色是 `0 16px 44px`（44 / 60），而那一行只有 `px-6 py-1`（24px / 4px），
  于是阴影被切出一条直线。
  实测被丢掉的像素：卡片左侧 30–46px 处原本是纯场景 `246,250,255`，
  留出位置后是 `241,245,251` / `244,248,253`。
  - **修法**：给滚动容器留够内边距，再用**等量负外边距**拉回来
    （`px-16 pt-10 pb-24` 配 `-mx-16 -mt-10 -mb-24`），布局零位移 ——
    实测卡片矩形前后完全一致（`548,435` → `548,435`）
  - 数字取自阴影自己的触达范围，**并且取两个主题里更远的那个**（暗色 64 / 40 / 88），
    不是取平均、也不是取亮色
  - **两个必须一起加的检查**：页面没多出横向滚动条、内边距与负外边距严格配平。
    负外边距会把行的边框盒撑到父元素之外，这是个真实的风险，不能只看"看起来没事"
  - **但这两个检查都抓不到「留得不够」** —— 配平断言只比较内边距与负外边距是否互相抵消。
    改了任何阴影 token 之后，必须**重新量一遍卡片旁边的像素剖面**，不能只看断言绿了
- **材质上的 `position: relative` 必须写在 `:where()` 里**（零特异性）。
  应用里有两处是 `mat-overlay absolute ...`（`DropdownMenu`、`Tooltip`），普通写法会
  按源码顺序盖掉 Tailwind 的 `absolute`，让所有下拉与 Tooltip 静默错位。详见 §9.2-12

#### 10.2.3 描边画在哪一像素上（v4.3.5）

用户报的现象：「首页的三张卡片，怎么我从视觉上看，是两层边线？」——**现象在卡片，根因在
`::after` 的 `inset` 解析基准**。这是本仓库第一条「像素级位置」规格，不是取值规格。

- **病因**：`--glass-edge` 走 padding-box 遮罩法，由 `::after` 承载。而**绝对定位元素的
  `inset` 是相对包含块的 padding box 解析的**，包含块就是材质自己；三种材质当时都带
  `border: 1px solid transparent`（描边原先的「槽位」），于是 padding box 比元素真正的边缘
  **内缩 1px**。同时表面的底色按默认的 `background-clip: border-box` **涂满那圈透明边框**，
  所以元素**看起来**到边框盒为止、描边却浮在里面 1px。实测剖面（亮色、两个主题四条边一致）：

  ```
  阴影 → 1px 纯表面色（那圈透明边框）→ 1px 描边 → 表面色
  ```

  在 125% 缩放下那 1px 带会变成约 1.25 设备像素，于是眼睛读到**两条线**。下缘最严重：
  `0 1px 2px` 的接触层在盒外又补了一条 `218,224,233`，与描边的 `219,229,240` 几乎同深。

- **修法**：把描边本身推进那圈透明边框里 —— `::after` 用 **`inset: -1px`**，描边于是成为
  元素最外那一像素，表面边缘 / 描边 / 裁剪边界三者在同一处。实测四条边都只剩一条线
  （亮色左 `548 rgb(219,229,240)`、右 `737 rgb(217,227,238)`、上 `435`、下 `566`；
  暗色同一条边分别是 `62,62,64` / `56,56,59` / `64,64,67` / `58,58,61`）。

- **⚠️ 不能靠「去掉边框」来修**（试过，退回了）：去掉边框后 padding box 与边框盒重合，
  描边位置确实正确，**但内容盒会各长 2px** —— 实测 26 个材质里 16 个位移，
  首页卡片 `548,435,190,132 → 548,436,190,130`，而且位移会**沿页面累积**
  （文生音页深处的内容上移 4px）。为了 1px 的发丝线动整个版式节奏，代价大于问题。
  保留边框 + `inset: -1px` 时 **26 个材质矩形完全一致（零位移）**。

- **两条「看起来更聪明」的绕法都试过，都留下了**：
  - **`background-clip: padding-box`**（让表面停在 padding box，于是带里没有纯底色）：
    面板保住了描边，但那条带露出的是元素**背后的东西**（外阴影不画进边框盒），
    比外侧的阴影还亮 —— 实测带 `244,248,253` 对阴影 `231,235,244`：
    一条亮线加一条暗线，**还是两层**。
  - **`border-image`**（想让边框直接成为描边）：**它无视 `border-radius`**。
    实测 60×60、`border-radius: 30px`、2px border-image：顶边中点是红的，
    而**角上 (1,1) 也是红的**（方形），普通边框在同一位置的角是未绘制的。直接排除。

- **⚠️ 会裁剪的材质必须换用 `.mat-clip`**：`overflow: hidden` 在后代的 **padding box**
  处裁剪，而描边住在最外那 1px（即边框带）里 —— 它会把描边**整条**吃掉，面板静默地少一条边线。
  `.mat-clip` 用 `overflow: clip` + **`overflow-clip-margin: 1px`** 把裁剪边界推到边框盒 + 1px，
  刚好放出描边这一条带。7 处（6 个面板 + `SpeechToText` 那张卡片）已改。

  - **裁剪本身是有用的，不能顺手删掉**。第一版测量说「首页松开裁剪有 882 个像素变化」，
    看起来铁证如山 —— 其实那是**词汇轮播正在换词**（热点在轮播区中央，不在任何边上）。
    重测时把轮播区排除并加一条「什么都不改」的基线：非轮播屏基线 **0 个像素**，
    首页基线 837~1013 个像素**全部落在轮播区内**。所以那条 882 是噪声，不是证据。
  - 逐像素比对「`overflow: hidden` vs `clip + 1px`」（6 屏 × 2 主题）：差异约 4300~6000 个像素，
    **全部在面板边缘 2px 内**（就是描边回来了）；另有约 88 个落在距边框盒 3~5px 处 ——
    那些是**圆角弧线上的描边抗锯齿**（半径 16px 内 0.7px 处，颜色只差 4~8 级），
    不是内容漏出。真正放开裁剪（`overflow: visible`）才会改变成百上千个**内容**像素。
  - **滚动容器是例外，而且是结构性的**：`overflow-clip-margin` 只对 `overflow: clip` 生效，
    所以一个必须滚动的材质（`AudioTagMenu` 那张 `max-h-[280px] overflow-y-auto` 的卡片）
    拿不到这条 1px —— 它**按设计没有描边**，只有阴影读出的边。这正是「同一个概念，
    用表面付得起的方向表达」，不是漏做。

- **验收**：不只是「看起来对」。`verify-rim` 对 6 屏 × 2 主题、**每个材质四条边**逐个采样
  11 个像素，问两条物理事实：**A** 最外那一像素相对盒内深处偏离 ≥8 级（那里确实画了描边）；
  **B** 在偏移 0..+4 内它的偏离最大（描边没被推到里面去）。**182/182 通过**。
  反向对照（把 `inset` 强行改回 `0`）**182/182 全部失败**，剖面里正是那条
  `0:246,250,255`（纯底色）→ `1:228,233,241`（描边）—— 没有这一步，「182 项通过」
  只证明脚本能跑完，不证明它测的是那件事（同 §9.2-19）。

- **静态门禁守的是「配对」**（`design-check.mjs` §5c/§5d）：三种材质**必须有** 1px 透明边框
  **且**共享 `::after` 的 `inset` 必须是 `-1px`。任何一半单独看都很自然，只有配对才正确 ——
  去掉边框（内容盒漂移）或把 `inset` 改回 `0`（两层边线）都会让那条带回来，而症状只是一条
  1px 的线，别的门禁和逐屏扫描都发现不了。另外静态断言 `.mat-clip` 的两条声明，
  并禁止 `mat-clip` 与任何 `overflow-*` 工具类同时出现（两者都在设 `overflow`，
  谁赢看源序，失败方式还是那条发丝线）。

#### 10.2.4 能测到什么程度

**先记一条前提：本仓库的测量机没有 GPU。** `SystemInfo.getInfo` 报
`glRenderer = "ANGLE (Microsoft, Microsoft Basic Render Driver …, D3D11)"`、
`gpu_compositing = disabled_software`、`rasterization = disabled_software` ——
所有帧时间都是**纯 CPU 软件栅格化**的最坏情况。**只有倍数和"谁导致的"可信，绝对值不可外推。**

模糊只在**背底变化**时付钱。实测（headless Chrome，软件合成，1422×864）：

| 情形 | 模糊开 | 模糊关 | 倍数 |
|---|---|---|---|
| 静止（真实使用） | 中位 16.7ms / p95 52.5ms | 中位 16.7ms / p95 18.0ms | **1.00x** |
| 背后持续运动（压力测试） | 中位 60.8ms | 中位 16.6ms | **3.66x** |
| 指针灯可见时（卡片 hover） | 52–57ms | 19ms | **一次 backdrop 重栅格/帧** |

结论：静止态中位帧时间与关掉模糊**完全相同**（16.7ms = 60fps），所以日常使用不付这个成本；
但静止态 p95 从 18ms 抬到 52ms，说明仍有约 5% 的帧被模糊拖慢。
指针灯的代价只发生在**鼠标停在一张卡片上并移动**的时候，不在面板上（面板不追踪，见上）。

  `rgba(255,255,255,0.95)`（合成后 `rgb(254,254,255)`），暗色主题下才是 `rgba(26,34,52,0.97)`。
  故彩点必须用 `-text` 变体（暗色主题下自动别名回原色），实测两主题均达标：
  浅色 danger/success/accent = 6.5 / 5.35 / 10.63:1，暗色 = 5.24 / 6.45 / 6.61:1
